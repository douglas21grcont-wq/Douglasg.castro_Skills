🎬 Acionamento Prático

Passo a passo: como você usaria /spec-driven no dia a dia

0

Cenário: Você identifica um problema

Está testando o Portal DG no celular e vê que a tela de Acompanhamento de Projetos está quebrada (layout horizontal, botões sobrepostos).

Você pensa: "Preciso de uma Spec clara disso para delegar para o agente"

1

Você Dispara a skill

Abre VS Code (ou Claude Code), digita:

/spec-driven

A skill carrega. Ela te pede informações ou oferece um template.

2

Skill Captura a Spec (interativa)

A skill tem 2 modos:

Modo A: Você traz pronto

Input esperado (você copia/cola):
--- projeto: Portal DG módulo: Acompanhamento de Projetos problema: Layout quebrado em mobile (≤768px) objetivo: 100% responsividade critérios: topbar sem overflow, tabelas scroll interno, botões ≥44px ---

Modo B: Skill guia (Q&A)

Skill faz perguntas:

Qual é o projeto? (Portal DG)
Módulo afetado? (Acompanhamento de Projetos)
Qual é o problema? (Layout quebra em mobile)
Qual é a restrição? (Design system azul, sem mudança em PHP)
Qual o breakpoint? (768px)

Skill consolida as respostas e monta a Spec estruturada.

3

Skill Cria documento de Spec

A skill gera um artifact com a Spec formatada (como o que fiz antes). Você revisa rápido.

Output (artifact):
Spec: Responsividade Mobile — Portal DG
• Problema: layout quebrado ≤768px
• Objetivo: 100% funcional mobile
• Critérios: 8 checklist items
• Regras: Design system + sem PHP
⏱ Tempo gasto: 2 minutos (você ou skill formando a Spec)
4

Skill Dispara agente

Skill faz as verificações finais ("Spec está clara?") e dispara o agente spec-executor:

Agent.spawn(spec_executor, { spec_url: artifact_da_spec, projeto: "Portal DG", modulo: "Acompanhamento de Projetos" })

Neste ponto, o trabalho pesado SAI da sua sessão. Agente roda isolado.

5

Agente: spec-executor Orquestra tudo

O agente executa o ciclo completo em paralelo:

5a. Opus: Plano
Lê a Spec, divide em 10 etapas. Volta com um plano detalhado.
5b. Sonnet: Executa
Pega o plano, aplica cada etapa. Edita os 4 arquivos (.php) do módulo, gerando código.
5c. Haikus: Auditam em paralelo
Enquanto Sonnet trabalha (ou depois), 3 Haikus validam:
• Haiku 1: "Tokens CSS respeitados?"
• Haiku 2: "Responsividade OK?"
• Haiku 3: "Acessibilidade OK?"
Cada um gera um relatório isolado.
5d. Consolida relatório
Agente junta tudo: código final + 3 auditorias + checklist de sucesso.
⏱ Tempo de agente: ~2-3 minutos (orquestra tudo, roda auditorias, retorna relatório)
6

Você Recebe o resultado

Agente envia uma notificação. Você vê um relatório consolidado:

Relatório Final (artifact):
✓ SPEC ATENDIDA

Código gerado:
• Acompanhamento_de_projetos/index.php — @media 768px
• Acompanhamento_de_projetos/projeto.php — topbar responsive
• Acompanhamento_de_projetos/editar.php — inputs 100%
• Acompanhamento_de_projetos/gantt.php — max-width

Auditorias:
✓ Tokens CSS — PASS (0 hardcoded colors)
✓ Responsividade — PASS (8/8 critérios)
✓ Acessibilidade — PASS (44px, tap targets)

Próximos passos:
1. Testar em dispositivo real (iPhone/Android)
2. Se OK → git add + commit
3. Atualizar handoff com lições aprendidas
7

Você Testa e aprova

Você abre o código gerado, testa em um dispositivo mobile real ou emulador:

cd "C:\Users\User\OneDrive - Planning\VS CODE\Portal DG\Portal-DG---Frontend_2.0" # Testar localmente (PHP server, Hostinger staging, etc) # Comparar com Spec: "Topbar cabe? Tabelas scrollam? Botões têm 44px?"

Se tudo OK, você aprova. Se houver problema, volta com feedback específico e o agente refina.

8

Você Faz o commit

VS Code → Source Control → Stage files → Commit com mensagem clara:

feat: responsividade mobile — Acompanhamento de Projetos - Topbar responsivo em ≤768px - Tabelas com scroll horizontal - Botões ≥44px (toque confortável) - Design system azul mantido - Sem mudança em PHP (0 regressão)

Você que faz o push (conforme suas regras).

9

Você Atualiza o handoff (próxima vez)

Cria um handoff.md com o que aprendeu:

## Responsividade Mobile — Concluído 2026-09-04 O que funcionou: - Usar Spec clara com critérios testáveis - @media 768px como breakpoint - Overflow-x: auto em tabelas (melhor que card conversion) O que não fazer: - Nunca truncar dados em mobile sem aviso - Não mexer em PHP (apenas CSS) Próxima vez: - Verificar responsive em gantt.php antes (é gráfico, complexo) - Testar com dados reais (100+ projetos)

Handoff é lido automaticamente na próxima iteração.

📊

Resumo: Fluxo Total

Você: /spec-driven (2 min)
Você/Skill: Captura Spec (1 min)
Skill: Monta Spec em artifact (1 min)
Skill: Dispara agente (instant)
Agente: Opus plano + Sonnet código + 3 Haikus auditam (2-3 min, paralelo)
Agente: Retorna relatório com código + auditorias (instant notification)
Você: Testa em device real (5-10 min, sua responsabilidade)
Você: Commit + push (1 min)
⏱ Tempo total esperado: 15-20 minutos (você) + 2-3 minutos (agente, paralelo)
Resultado: Código gerado + auditado + pronto para produção
❓

Perguntas frequentes sobre esse fluxo

P: E se o agente errar?
R: Você vê no relatório qual auditoria falhou. Refina a Spec ("não use overflow-x, use grid mobile") e dispara de novo.
P: Preciso saber o que o agente fez antes de testar?
R: Sim. Agente gera um diff legível. Você revisa a lógica (CSS) antes de testar. Não é caixa-preta.
P: Posso usar isso para outros projetos (Nilo, Profarm)?
R: Sim! Spec funciona pra tudo. Mude só projeto/módulo/critérios na captura.
P: E se não tiver handoff no começo (como agora)?
R: Sem problema. Spec é clara o suficiente. Handoff é bonus para iterações futuras.
